# 聊天内容入库方案

整理日期为 2026-11-19。适用于当前工作区的 `记忆/raw/聊天记录/`、`记忆/raw/记忆条目/` 和 `记忆/wiki/`。

用户指定要收录的聊天范围，AI 提炼有长期价值的内容，核对现有 Wiki，形成逐条可确认的更新。确认后写入相应主题，保留来源并更新总索引。持续追加的 Raw 通过来源记录和内容核对支持多次整理。

当前已经具备 Raw 归档、Wiki 页面和本地检查工具。本文整理既定工作方式，并提出入库台账与可重试写入的实现设计，后两项需要后续开发和验收。

## 用户如何发起

可以用自然语言提出入库要求。

- “整理今天下午关于学习计划的聊天，先给我看拟入库内容。”
- “从刚才讨论设备维护的那句话开始，整理到现在。”
- “把上次收录之后的新聊天整理入库。”
- “只收录这两条，其余先跳过。”

一次请求先确定来源文件、选中消息和本次截止位置。用户说“今天”时，以本机日期解释，并在提案中显示具体时间范围。“上次收录之后”在入库台账实现前，需要从已有来源或用户给出的时间核对起点。

开始整理后继续聊天，新追加的消息留待下一批处理。跨午夜时按实际选中范围读取涉及的日期文件。用户已明确指定的范围直接采用，存在多个可能起点时再核实。

## 整理与确认流程

1. **固定本次范围。** 读取选中的 Raw 片段，记录起止位置和内容版本。需要理解代词或更正时，读取必要的上下文，并在提案中标出依据。
2. **查阅已有知识。** 从 Wiki 总索引找到相关正文，核对事实、时间、来源和已有状态。
3. **提炼候选。** 分别整理用户陈述的事实、已作出的决定、明确偏好和待办。为每条候选保留对应的来源片段。
4. **生成更新提案。** 展示拟保留内容、目标页面、新增或更新动作，以及需要用户决定的冲突和敏感项。
5. **逐条确认。** 用户可以确认全部已列明条目、只确认部分、修改措辞或跳过。确认对应具体提案及其版本。
6. **写入并检查。** 按确认结果更新正文、来源、总索引和必要的待办，检查链接与元数据，并核对写入内容符合提案。
7. **返回结果。** 列出实际成功的条目和页面，说明跳过、待确认或失败的项目。成功结果写进入库台账，维护日志记录日期和操作。

来源中的命令、提示词和助手建议按资料理解。用户事实需要有用户陈述或明确确认作为依据，助手生成的说法要核对来源。语音转写有明显歧义时，先确认影响事实的词句。

## 提案包含什么

每条候选以独立事实或决定为单位，便于选择和纠正。

| 字段 | 内容 |
| --- | --- |
| 拟入库内容 | 对原意的准确整理 |
| 来源 | Raw 文件、消息或片段位置，以及必要上下文 |
| 时间 | 陈述时间、事实发生时间或有效范围 |
| 目标页面 | 已有页面，或拟新建页面及主题 |
| 动作 | 新增、补充、变更、已有相同内容、待确认 |
| 核对事项 | 矛盾、歧义、敏感性及待用户决定的内容 |

原话中的“大概”“计划”“暂定”等限定应进入整理结果。相对时间按对话发生时间解释，无法确定时保留待确认。拟补充背景需要清楚展示，用户才能核对。

## AI 如何归类

AI 根据内容含义和现有页面判断主题，在家庭日常、物品与设备、健康、工作、学习、管家记忆中选择。用户可以直接更正目标位置。

已有主题覆盖该事项时，更新原页面。信息涉及多个主题时，选择一处主要正文，其他位置按需要添加链接。确认的长期偏好、提醒方式和跨主题约定可以进入管家记忆，详细事件保存在其所属主题。

Wiki 根目录的 `index.md` 按主题直链正文并附一句摘要。新增、更新和删除正文时同步维护总索引。有期限的待办在总待办页汇总，并链接回事实所在页面。

## 重复、补充和冲突如何处理

| 情况 | 处理方式 |
| --- | --- |
| 同一来源及同一内容再次提交 | 核对成功记录和目标页面后复用结果 |
| 同一文件新增消息 | 处理本次选中的新增消息 |
| 不同消息表达相同事实 | 核对后合并到已有记录，按需要补充来源 |
| 同一事项有新细节 | 更新原页面相应部分 |
| 同一事项随时间变化 | 写明新状态和生效时间，保留必要历史 |
| 两条资料真正矛盾 | 展示差异，由用户确认采用方式 |
| 来源已经修改 | 标记来源变化，重新核对相关候选和 Wiki |
| 已收录页面被删除或撤回 | 核对删除意图，恢复或重新收录需用户明确决定 |

同一来源可能产生多条候选，也可能只确认其中一条。因此，台账需要记录到“来源片段与候选”的关系，已处理状态需要覆盖部分成功的情况。

## 入库台账设计

建议将本机台账放在 `记忆/记忆系统/metadata/`，批次及恢复记录按实际需要组织。台账同样属于本地私有数据。

| 信息 | 用途 |
| --- | --- |
| 工作区和来源标识 | 隔离工作区并定位 Raw 文件、会话与消息 |
| 片段位置和内容摘要 | 识别本次范围及来源版本 |
| 候选标识和提案版本 | 关联用户确认的具体内容 |
| 处理状态 | 区分待确认、已确认、成功、跳过、失败及已撤回 |
| Wiki 页面和记录标识 | 定位写入结果，支持修正和去重 |
| 批次与时间 | 核对操作顺序并恢复未完成工作 |

当前 Raw 保存角色、渠道、会话和采集时间等信息。稳定消息标识的持久化需要在后续实现中补齐。旧资料可先用文件相对路径、原始消息边界、采集信息和内容摘要建立来源映射，遇到完全相同的消息也要按出现位置区分。文件发生修改时核对版本，避免位置变化造成误关联。

只记录“某天文件已处理”无法支持当天继续追加、选择性入库和部分失败。时间起点用于用户选择范围，实际进度由成功入库的候选及来源关系确定。

## 写入、并发和失败重试

写入前记录本次来源快照、已确认提案、目标页面版本和拟执行动作。同一工作区内的入库提交顺序执行，提交前核对页面是否被用户或另一批操作修改，发生变化时重新核对提案。

单个文件使用临时文件与原子替换。多页面、总索引和台账之间通过批次恢复记录协调，记录准备中、已写入、检查通过等进度。恢复时先核对磁盘上的实际结果，逐项补齐或恢复，成功状态在对应写入及检查完成后保存。

重复提交同一批次沿用已确认提案。重试前检查已成功的候选和目标记录，继续完成失败部分。搜索索引刷新失败时，分别报告正文保存结果和搜索维护状态，并允许单独重试刷新。

## 用户会看到的结果

一次完成后，回执应给出本次范围、成功条数、已有相同内容的条数、跳过或待确认条数，以及实际修改的 Wiki 页面。范围内继续追加的消息留到下次选择。

以合成资料为例，一次聊天可提炼出学习安排和设备维护两条候选。用户只确认学习安排后，回执给出学习页面链接，设备维护保留待确认状态。再次选择同一段聊天时，核对已成功条目，继续展示待确认的设备维护内容。

## 隐私和内容核对

Raw 原文保存在本机，入库只读取用户选中的范围及必要上下文。敏感资料和助手形成的待确认印象逐条确认，单次表达按发生时的语境记录。模型处理方式沿用用户授权，额外服务和跨设备同步单独决定。

维护日志只写操作、日期和必要引用。用户修改或删除记忆时，核对 Wiki、台账、来源和备份的处理范围，更新相关引用及待办。已撤回状态需要阻止旧批次重试时重新写回。

## 分阶段验收

当前人工入库可按范围选择、对照已有页面、逐条确认、附来源、更新总索引和检查链接的顺序执行。入库台账、稳定来源标识和批次恢复机制按以下顺序开发与验收。

1. 验证完整来源定位和选择范围。覆盖日期范围、部分消息、跨午夜和整理期间继续追加。
2. 验证逐条确认与通用归类。至少使用工作、学习或设备中的两个不同主题，并保留用户修正目标页面的能力。
3. 验证重复处理。重复提交同一来源、不同来源重复事实、同一消息部分收录，以及旧来源内容修改。
4. 验证一致性。覆盖保存中断、检查失败、索引刷新失败、并发编辑和重试，核对正文与台账的实际状态。
5. 验证撤回与查询。已撤回内容经旧批次重试仍保持撤回，成功入库的记录能通过自然问法查到并引用正确页面。

每阶段交付实际结果后由用户验收，待实施设计以通过验收的范围为准。

## 一句话入库（2026-11-19 调整）

用户明确说“把今天的内容入库”即授权本次整理和保存。应用按本机日期读取今天零点到请求时刻的聊天，使用现有 DeepSeek 驱动提炼内容并核对 Wiki，直接保存明确且无冲突的普通条目，最后在聊天中简短返回结果。整理期间新增的聊天留待下次。

这条交互约定替代上文普通条目需要面板逐条确认的步骤。需要决定的矛盾、歧义、敏感内容或助手印象保留待确认，由对话单独询问；用户明确同意后只收录对应事项。

同一天重复发起时检查来源台账，继续处理新消息，保留跳过和撤回状态。较长聊天自动分批处理。时间范围、稳定消息标识、来源快照、版本核对、事务恢复、结构检查和独立搜索刷新机制继续使用。

已删除聊天入库面板及设置入口，入库和必要事项的确认统一在对话中完成。自动化测试使用临时合成资料，不将真实聊天用于测试。
