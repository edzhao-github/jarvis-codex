# LLM Wiki

> 译注：本文是 Andrej Karpathy《LLM Wiki》的完整中文翻译，非作者官方译本，未加入本项目的适配规则。英文原文见同目录《原版提示词.md》。原始来源：https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f 。下文中的“我”指原作者，观点、产品描述和效果判断均按原文保留，不代表已在本项目验证。

一种利用大语言模型（LLM）构建个人知识库的模式。

这是一份构想文件，设计用途是直接复制粘贴给你自己的 LLM Agent，例如 OpenAI Codex、Claude Code、OpenCode / Pi 等。它旨在传达高层思路，具体细节则由你的 Agent 与你协作构建。

## 核心思路

大多数人与 LLM 和文档打交道的方式类似 RAG（检索增强生成）：上传一批文件，LLM 在查询时检索相关片段，再生成答案。这种方式可行，但每提出一个问题，LLM 都要从头重新发现知识，没有积累。如果你问一个需要综合五份文档才能回答的细致问题，LLM 每次都得寻找并拼接相关片段，什么也没有沉淀下来。NotebookLM、ChatGPT 的文件上传功能，以及大多数 RAG 系统，都是这样工作的。

这里的思路有所不同。LLM 不再只是在查询时检索原始文档，而是**逐步构建并维护一个持久存在的 Wiki**：一组结构化、相互关联的 Markdown 文件，处在你与原始资料之间。加入新资料时，LLM 不只是为它建立索引以供以后检索，而是阅读资料、提取关键信息，并将其整合进已有 Wiki：更新实体页面、修订主题摘要、记录新数据与旧说法的矛盾，并强化或质疑不断演进的综合认识。知识被编译整理一次，之后持续保持更新，而不是每次查询都重新推导。

这就是关键区别：**Wiki 是一种持久存在、价值会不断累积的成果。**交叉引用已经建立，矛盾已经标出，综合认识已经反映了你读过的全部材料。每加入一份资料、每提出一个问题，Wiki 都会变得更加丰富。

你自己不必，或者很少需要，编写 Wiki——全部内容由 LLM 编写和维护。你负责收集资料、探索和提出恰当的问题。LLM 则承担所有繁琐工作：总结、交叉引用、归档和维护记录，让知识库随着时间推移真正发挥作用。实际使用时，我一边打开 LLM Agent，另一边打开 Obsidian。LLM 根据我们的对话修改内容，我则实时浏览结果：沿着链接阅读、查看关系图、阅读更新后的页面。Obsidian 是 IDE，LLM 是程序员，Wiki 是代码库。

这套方式适用于很多场景，例如：

- **个人事务**：跟踪自己的目标、健康、心理和自我提升情况；归档日记、文章、播客笔记，逐渐形成对自己的结构化认识。
- **研究**：在数周或数月内深入一个主题；阅读论文、文章和报告，逐步建立全面的 Wiki，并形成不断演进的研究论点。
- **读一本书**：随着阅读进度归档各章，为人物、主题、情节线及其关联建立页面。读完时，你就拥有了一套丰富的伴读 Wiki。可以想想 [Tolkien Gateway](https://tolkiengateway.net/wiki/Main_Page) 这样的爱好者 Wiki：志愿者社区多年积累了数千个相互关联的页面，涵盖人物、地点、事件和语言。你也可以在阅读时为自己建立类似的东西，交叉引用和维护工作交给 LLM。
- **企业／团队**：由 LLM 维护内部 Wiki，以 Slack 讨论串、会议转录、项目文档和客户通话等为输入，也可以由人参与审核更新。LLM 接手了团队成员都不愿做的维护工作，因此 Wiki 能持续保持更新。
- **竞品分析、尽职调查、旅行规划、课程笔记、深入研究兴趣爱好**：凡是需要长期积累知识，并希望让知识井然有序而不是四处散落的事情，都适用。

## 架构

共有三层：

**原始资料（Raw sources）**：你精心选择和收集的源文档，包括文章、论文、图片和数据文件。这些资料保持不变：LLM 可以阅读，但绝不修改。它们是事实依据。

**Wiki 层**：由 LLM 生成的一组 Markdown 文件，包括摘要、实体页面、概念页面、比较、概览和综合分析。这一层完全由 LLM 负责。它创建页面，在新资料到来时更新内容，维护交叉引用，保持整体一致。你阅读，LLM 编写。

**组织与维护规范（Schema）**：一份告诉 LLM 如何组织 Wiki、遵循哪些约定，以及在吸收资料、回答问题或维护 Wiki 时采用哪些工作流的文档，例如 Claude Code 的 CLAUDE.md 或 Codex 的 AGENTS.md。这是关键配置文件：它让 LLM 成为有章法的 Wiki 维护者，而不是泛泛的聊天机器人。随着你们逐渐找到适合自己领域的方式，你与 LLM 会共同改进这份规范。

## 操作

**吸收资料（Ingest）**：你把新资料放进原始资料集合，让 LLM 处理。一个示例流程是：LLM 阅读资料，与你讨论关键收获，在 Wiki 中编写摘要页，更新索引，更新各处相关的实体和概念页面，并追加一条日志。单份资料可能涉及修改 10—15 个 Wiki 页面。我个人更喜欢每次处理一份资料，并持续参与：阅读摘要、检查更新、指导 LLM 应该突出什么。但你也可以一次批量吸收很多资料，减少监督。你需要形成适合自己风格的工作流，并将它记录在规范中，供以后的会话使用。

**查询（Query）**：你针对 Wiki 提问。LLM 搜索并阅读相关页面，综合生成带有来源引用的答案。根据问题不同，答案可以是 Markdown 页面、对比表格、幻灯片（Marp）、图表（matplotlib）或画布。关键认识是：**好的答案可以作为新页面归档回 Wiki。**你要求的一次比较、一份分析、一个新发现的关联，都有价值，不应该消失在聊天记录里。这样，你的探索也会像新吸收的资料一样，持续为知识库积累价值。

**检查维护（Lint）**：定期让 LLM 为 Wiki 做一次健康检查，查找页面之间的矛盾、已被新资料取代的过时说法、没有入站链接的孤立页面、被提及却没有独立页面的重要概念、缺失的交叉引用，以及可通过网络搜索补齐的信息空白。LLM 擅长建议值得进一步研究的新问题和新资料。这能让不断增长的 Wiki 保持健康。

## 索引与日志

随着 Wiki 增长，两个特殊文件帮助 LLM 和你在其中导航，它们各有用途：

**index.md** 面向内容。它是 Wiki 所有内容的目录：每个页面都有链接和一句话摘要，还可以附上日期、资料数量等元数据。按类别组织，例如实体、概念、资料等。LLM 每次吸收资料都更新它。回答查询时，LLM 先读取索引以找到相关页面，再深入阅读。在中等规模——大约 100 份资料、数百个页面——下，这种做法效果出人意料地好，而且不必搭建基于嵌入向量的 RAG 基础设施。

**log.md** 按时间组织。它是一份只追加、不覆盖的记录，记下什么时候发生了什么：吸收资料、查询、检查维护等。一个实用技巧是让每条记录使用统一前缀，例如 `## [2026-04-02] ingest | Article Title`，这样就可以用简单的 Unix 工具解析日志：`grep "^## \[" log.md | tail -5` 可以显示最近五条记录。日志提供了 Wiki 演变的时间线，帮助 LLM 了解近期已经完成的事情。

## 可选：命令行工具

到某个阶段，你可能想开发一些小工具，帮助 LLM 更高效地操作 Wiki。最直观的是 Wiki 页面搜索引擎：规模小时索引文件足够，Wiki 变大后就需要完善的搜索功能。[qmd](https://github.com/tobi/qmd) 是一个不错的选择：它是面向 Markdown 文件的本地搜索引擎，支持 BM25 与向量混合搜索，以及 LLM 重排序，全部在设备本地完成。它既有 CLI，让 LLM 可以通过 Shell 调用，也有 MCP 服务端，让 LLM 可以将其作为原生工具使用。你也可以自己做一个更简单的版本：有需要时，让 LLM 帮你用自然语言驱动编程，写出一个基础搜索脚本。

## 技巧与建议

- **Obsidian Web Clipper**：一个将网页文章转换为 Markdown 的浏览器扩展，适合快速把资料收进原始资料集合。
- **将图片下载到本地**：在 Obsidian 的“设置 → 文件与链接”中，将“附件文件夹路径”设为固定目录，例如 `raw/assets/`。然后在“设置 → 快捷键”中搜索“Download”，找到“Download attachments for current file”（下载当前文件的附件），绑定一个快捷键，例如 Ctrl+Shift+D。剪藏文章后按一下快捷键，所有图片便会下载到本地磁盘。这是可选步骤，但很实用：LLM 可以直接查看并引用图片，不必依赖可能失效的 URL。注意，LLM 无法原生地一次读取带有行内图片的 Markdown；变通做法是先读文本，再单独查看部分或全部被引用的图片，获得更多上下文。虽然有些笨拙，但足够好用。
- **Obsidian 的关系图视图**：最适合查看 Wiki 的整体结构，了解哪些内容彼此相连，哪些页面是枢纽，哪些是孤立页面。
- **Marp**：一种基于 Markdown 的幻灯片格式，Obsidian 有对应插件，适合直接从 Wiki 内容生成演示文稿。
- **Dataview**：一个可查询页面 frontmatter（文件头部元数据）的 Obsidian 插件。如果 LLM 为 Wiki 页面添加 YAML frontmatter，例如标签、日期和资料数量，Dataview 就能生成动态表格和列表。
- Wiki 本质上只是一个存放 Markdown 文件的 Git 仓库，因此自然就能获得版本历史、分支和协作能力。

## 为什么这套方式有效

维护知识库最烦琐的部分不是阅读或思考，而是日常整理：更新交叉引用、让摘要保持最新、记录新数据与旧说法的矛盾，以及维护数十个页面之间的一致性。人们放弃 Wiki，是因为维护负担增长得比价值更快。LLM 不会厌烦，不会忘记更新交叉引用，而且一次就能修改 15 个文件。维护成本接近零，因此 Wiki 能持续得到维护。

人的工作是选择资料、指导分析、提出好问题，并思考这些内容意味着什么。其他工作由 LLM 完成。

这一思路在精神上接近 Vannevar Bush 在 1945 年提出的 Memex：一种由个人精心组织的知识存储，通过联想路径把文档连接起来。相较于后来互联网的样子，Bush 的设想更接近这里的模式：私有、主动整理，文档之间的联系与文档本身一样有价值。他当时没能解决的是谁来维护，LLM 可以承担这项工作。

## 说明

本文有意保持抽象。它描述的是思路，而不是具体实现。确切的目录结构、规范约定、页面格式和工具，都取决于你的领域、偏好，以及选择的 LLM。以上内容全部是可选且模块化的：挑选有用的，忽略不需要的。

例如，你的资料可能只有文本，因此完全不需要图片处理。你的 Wiki 可能小到只靠索引文件就足够，不需要搜索引擎。你可能不关心幻灯片，只想要 Markdown 页面。你也可能希望采用完全不同的输出格式。正确的使用方式是把这份文档交给你的 LLM Agent，一起构建适合你需求的版本。这份文档唯一的任务就是传达这种模式，剩下的事情你的 LLM 可以想办法完成。
